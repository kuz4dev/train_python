# Git и GitHub: основы

## Зачем нам это вообще нужно?

Представьте, что вы пишете большой реферат. Сначала был файл `реферат.docx`, потом `реферат_финал.docx`, потом `реферат_финал_2.docx`, потом `реферат_точно_финал.docx`... Знакомо? А если над рефератом работают сразу пять человек — вообще катастрофа.

**Git** — это программа, которая решает эту проблему. Она запоминает все изменения в ваших файлах: кто, что и когда поменял. Можно в любой момент вернуться к старой версии, посмотреть историю или работать над проектом вдвоём, не наступая друг другу на ноги.

**GitHub** — это сайт в интернете, куда можно загрузить свой проект, чтобы он хранился не только на вашем компьютере. Это как Google Диск, но специально для программистов. Если компьютер сломается — код останется в безопасности.

> Простая аналогия: **Git** — это машинка времени для вашего кода. **GitHub** — это облачное хранилище, где эта машина времени живёт и куда могут заглянуть другие люди.

## Главные понятия

### Репозиторий (repository, или просто «репа»)

Репозиторий — это папка с вашим проектом, за которой следит Git. Внутри есть все файлы проекта плюс невидимая папка `.git`, где Git хранит всю историю изменений.

### Коммит (commit)

Коммит — это «снимок» вашего проекта в определённый момент. Что-то вроде сохранения в компьютерной игре. Сделали важный кусок работы — сохранились (сделали коммит). Если что-то сломается — можно загрузиться с последнего сохранения.

У каждого коммита есть сообщение — короткое описание, что именно вы поменяли. Например: «Добавил кнопку входа» или «Исправил ошибку с подсчётом цены».

### Ветка (branch)

Представьте, что вы пишете книгу и хотите попробовать переписать одну главу по-другому. Но и старый вариант терять не хочется. Что делать? Создать копию книги и менять её. Если новый вариант понравится — заменим им старый. Если нет — выбросим копию.

В Git это называется **ветка**. Главная ветка обычно называется `main` (раньше была `master`). От неё можно «отращивать» свои ветки, экспериментировать, а потом либо вливать их обратно, либо удалять.

### Удалённый репозиторий (remote)

Это копия вашего репозитория, которая лежит где-то в интернете — например, на GitHub. Вы можете отправлять туда свои изменения (`push`) или забирать оттуда чужие (`pull`).

## Как Git думает о ваших файлах

У каждого файла в репозитории есть три возможных состояния:

1. **Рабочая директория** — то, что вы видите в папке и редактируете прямо сейчас.
2. **Индекс (staging area)** — «корзинка», куда вы складываете файлы, которые хотите сохранить в следующем коммите.
3. **Репозиторий** — то, что уже зафиксировано в истории.

Это самая важная для понимания вещь. Когда вы поменяли файл — он ещё не в коммите. Сначала вы кладёте его в корзинку (`git add`), потом «оплачиваете покупку» — делаете коммит (`git commit`).

```
[редактирую файл] → git add → [корзинка] → git commit → [история]
```

## Базовые команды

### Настройка (один раз на всю жизнь)

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "you@example.com"
```

Git будет подписывать ваши коммиты этим именем.

### Создать новый репозиторий

```bash
git init
```

Запускаем в папке с проектом — и она становится репозиторием.

### Скопировать чужой репозиторий с GitHub

```bash
git clone https://github.com/user/project.git
```

Скачивает весь проект со всей историей на ваш компьютер.

### Посмотреть, что изменилось

```bash
git status
```

Главная команда, которой будете пользоваться всё время. Показывает, какие файлы изменены, что лежит в корзинке, а что — ещё нет.

### Положить файл в корзинку

```bash
git add имя_файла.py
git add .                  # положить вообще всё изменённое
```

### Сделать коммит

```bash
git commit -m "Описание того, что я сделал"
```

Сообщение должно быть осмысленным. Не `"коммит"` и не `"исправил"`, а `"Добавил проверку пароля при регистрации"`.

### Посмотреть историю коммитов

```bash
git log
git log --oneline          # покороче, по строчке на коммит
```

### Отправить изменения на GitHub

```bash
git push
```

### Забрать изменения с GitHub

```bash
git pull
```

Нужно, если кто-то ещё работает над проектом и уже что-то загрузил, или если вы сами работаете с двух компьютеров.

### Работа с ветками

```bash
git branch                       # список веток
git branch новая_ветка           # создать ветку
git checkout новая_ветка         # переключиться на неё
git checkout -b новая_ветка      # создать и сразу переключиться
git merge другая_ветка           # влить другую ветку в текущую
```

## Типичный рабочий цикл

Допустим, мы делаем сайт и хотим добавить страницу контактов.

```bash
git status                            # посмотрели, что и как
git checkout -b contacts-page         # создали ветку под задачу
# ... пишем код, делаем страницу ...
git status                            # проверили изменения
git add .                             # положили всё в корзинку
git commit -m "Добавила страницу контактов"
git push                              # отправили на GitHub
```

Дальше на GitHub можно открыть **Pull Request** — запрос «влить мою ветку в основную». Это удобно, когда работаете в команде: коллеги посмотрят код, обсудят и нажмут «принять».

## Что такое GitHub конкретно

GitHub — это сайт, где живут репозитории. Что там можно делать:

- **Хранить код** в интернете, бесплатно.
- **Показывать свои проекты** — будущему работодателю, друзьям, всему миру.
- **Работать в команде** — несколько человек редактируют один проект.
- **Issues** — список задач и багов проекта. Что-то вроде доски с записками «не работает кнопка», «надо добавить тёмную тему».
- **Pull Request** — предложение изменений, которое обсуждают и принимают.
- **README.md** — главный файл-визитка проекта. То, что видит человек, открывший вашу репу.

## Полезные мелочи

### Файл `.gitignore`

Иногда есть файлы, которые в репозиторий попадать не должны: пароли, временные файлы, кэш. Создаём в корне проекта файл `.gitignore` и пишем туда имена и шаблоны:

```
__pycache__/
*.pyc
.env
venv/
```

Git будет делать вид, что этих файлов вообще нет.

### Если что-то пошло не так

```bash
git checkout -- имя_файла       # отменить изменения в файле (вернуть как было)
git reset имя_файла              # вынуть файл из корзинки
git log --oneline                # найти нужный коммит и его хэш
```

Главное правило: **если запутались — сначала `git status`**. Эта команда почти всегда подсказывает, что делать дальше.

---

## Что запомнить

- **Git** хранит историю проекта. **GitHub** — это сайт, где этот проект лежит.
- Сохраняйтесь часто — каждый коммит это бесплатная страховка.
- Пишите внятные сообщения к коммитам. Через неделю вы сами не вспомните, что значит «фиксы».
- Для отдельных задач делайте отдельные ветки — основной код всегда должен быть рабочим.
- Команда `git status` — ваш лучший друг.

Дальше можно изучать более продвинутые штуки: `rebase`, конфликты слияния, теги, форки. Но того, что в этой лекции, уже хватит, чтобы спокойно работать со своими проектами и заливать их на GitHub.
